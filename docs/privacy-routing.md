# DNS and routing

Both client renderers share endpoint, resolver and policy selection. The sing-box renderer emits typed DNS servers and route actions. Mihomo gets its native nameserver, resolver-policy, proxy groups and rule fields. Exporting a proxy provider serializes nodes only; DNS and groups belong in the containing Mihomo config.

```sh
sudo singforge dns set --profile strict --resolver quad9 --transport https --family ipv6 --capture tun
sudo singforge dns show
sudo singforge rules update
sudo singforge rules set --profile smart
sudo singforge rules override --kind DOMAIN-SUFFIX --value example.org --group AI
sudo singforge rules test --host sub.example.org
```

Supported public resolvers are Google, Cloudflare and Quad9. The rendered encrypted resolver uses a literal IP to bootstrap without an OS lookup. Choose IPv4 or IPv6 according to the **client's** available network. sing-box sets the TLS server name explicitly. Mihomo uses the resolver's IP HTTPS or TLS endpoint. On the server, domain destinations resolve through typed Cloudflare DoH. Set `--server-family ipv6` on an IPv6-only host with a DNS hostname. Client resolver family is configured separately. The main remote resolver is explicitly routed through the Main proxy selector. Resolving an upstream proxy hostname has a separate encrypted direct bootstrap path; this reveals the proxy hostname and the client's IP to that resolver. An IP endpoint avoids this lookup.

Strict config has no ISP fallback. The full strict Mihomo profile disables system-hosts overrides so stale OS entries cannot redirect proxy hostnames. Balanced mode may use system hosts. Balanced mode sends only local, lan and home.arpa suffixes to the system resolver, which trades local DNS privacy for local naming. Mihomo additionally returns real IPs for the explicitly listed connectivity-check hosts. Fake-IP filtering affects the answer presented to the application; DNS upstream selection is a separate policy. In TUN capture mode sing-box uses a typed Fake-IP server for intercepted A/AAAA, local-domain rules first, and 53 interception. Both client TUN configurations need host permissions. Full Mihomo exports enable TUN by default unless `--capture system` was explicitly selected. Native sing-box enables TUN only with `--capture tun`. The mixed proxy listener stays on loopback. A browser or program ignoring the proxy may still use system DNS; applications with independent DoH can bypass the client's DNS rules, particularly in system-proxy mode. IPv6 outside a captured default route is another bypass.

To investigate leaks, use a domain you control and a fresh random label. Observe authoritative queries and capture physical-interface traffic while testing with and without the proxy. Watch UDP/TCP 53, 853, resolver HTTPS connections and both IP families. Compare browser DoH on/off, test proxy loss and check that sensitive names fail closed. `dns test --host NAME --port 1053` queries a running local client DNS listener on the machine running the command. Its answer alone cannot identify every application or upstream path.

## Chrome WebRTC privacy on macOS

WebRTC can expose your ISP's public IP to a website even when the page itself loads through a proxy. The optional [Chrome WebRTC privacy profile](../examples/macos/Chrome-WebRTC-Privacy.mobileconfig) sets `WebRtcIPHandling` to `disable_non_proxied_udp` for Google Chrome under the current macOS user. Calls may need a TCP relay or fail when a service requires direct UDP.

1. Open the downloaded `.mobileconfig` file. In System Settings, search for **Device Management** or **Profiles**. Review the unsigned **Chrome WebRTC 隐私** profile and choose **Install**.
2. In your usual Chrome profile, visit `chrome://policy`, click **Reload policies**, and confirm that `WebRtcIPHandling` has the value `disable_non_proxied_udp` and status **OK**.
3. Repeat your WebRTC leak test in that browser. Check that the WebRTC candidates omit your ISP's public IP. An empty candidate list is also an acceptable privacy result.
4. To undo the change, remove **Chrome WebRTC 隐私** in the same System Settings pane, reload Chrome policies, and check the effective value again.

In an isolated Chrome test, the underlying preference suppressed direct STUN packets and the resulting server-reflexive candidate. The sample profile has passed plist syntax and payload checks. Steps 2 and 3 verify the effective policy and browser behavior after manual installation.

## Rule semantics

The built-in smart profile works offline. Users can select AI, Streaming and Communication separately in the full client. Overrides precede service rules. Service rules precede broad geographic rules. The smart fallback is Main. Global defaults to Main. GFW-only requires a downloaded GFW list, sends its matches through Main and otherwise uses DIRECT. Custom uses the operator's ordered overrides and a Main fallback. For Mihomo, explicitly DIRECT traffic can resolve via the direct resolver list. Direct resolution follows nameserver-policy, including explicit AI protections.

Full Mihomo subscriptions send the final MATCH to the Unmatched selector. Its first choice follows the preset fallback described above. The client can switch between Main and DIRECT. Smart classifies Cursor, Antigravity, Gemini and GitHub Copilot service endpoints before geographic routing. Shared Google sign-in and asset hosts listed in the policy use Main. Endpoint references include the [Gemini firewall settings](https://knowledge.workspace.google.com/admin/generative-ai/gemini-app/gemini-app-firewall-settings), [Antigravity enterprise endpoints](https://antigravity.google/docs/enterprise), [Cursor network configuration](https://cursor.com/docs/enterprise/network-configuration), [Copilot allowlist](https://docs.github.com/en/copilot/reference/copilot-allowlist-reference) and [Google AI domain list](https://github.com/v2fly/domain-list-community/blob/master/data/google-deepmind).

Smart Mihomo uses `category-ai-!cn` and `category-ai-cn` from the client GeoSite database after explicit services and before general platform domains. International category DNS uses AI. Category-only domestic AI matches use the normal DNS policy, including CN membership in split and domestic-first modes. Explicit domain and suffix exceptions respect routing order when constructing DNS policy. The CLI explains explicit rules and identifies outcomes that depend on client geodata or the Unmatched selection.

Full Smart Mihomo exports use the Google and Google-CN GeoSite categories for shared Google hosts, replacing 25 exact entries. The international AI and Gemini DNS categories precede Google, Google-CN and CN. YouTube and Apple TV traffic matches Streaming before broad platform categories. Apple CN, Apple Update and mzstatic.com select DIRECT for connections; DNS for these hosts follows the existing DNS policy. Native sing-box retains the exact Google entries.

Mihomo uses its native `GEOSITE,CN` and `GEOIP,CN,no-resolve` rules after explicit service rules. They replace the generated lists of more than 120,000 domain and CIDR entries. Mihomo refreshes its GeoSite and GeoIP data from the documented MetaCubeX sources every 24 hours. Sing-box downloads cached CN SRS rule sets from the format-specific MetaCubeX `sing` branch on the same interval. The subscription carries the rule-set URLs and small configurations rather than geographic payloads. In split and domestic-first modes, CN GeoSite membership also selects the regional DNS policy for ordinary lookups. The GeoIP rule only determines the connection exit. AI and service rules always match before the geographic rules. Geographic downloads are HTTPS authenticated third-party data. Availability and data correctness remain dependent on that upstream.

Maintained sources and revisions appear in [the upstream review](research.md). Client-side policy sets derived from external rule data retain that data's licensing obligations.

## Mihomo DNS and failover

```sh
sudo singforge dns set --mihomo-policy split --mihomo-ipv6 off
```

Full Mihomo subscriptions use separate lists for encrypted bootstrap, proxy hostnames and application queries. For the strict policy, `default-nameserver` uses authenticated IP endpoints operated by Cloudflare, Google and Quad9. The configured resolver is listed first; Mihomo can query multiple upstreams concurrently. Proxy-server lookups use the configured international IP resolvers through DIRECT by default to avoid a DNS/proxy dependency loop. Application queries use the Main group, and known AI domain policies explicitly use the AI group. No DNS fallback list includes domestic or ISP resolvers.

`--mihomo-policy strict` leaves domestic public DNS unused. Both split and domestic-first use multiple operators to bootstrap resolver hostnames. With smart routing, `geosite:cn` queries use regional encrypted endpoints directly and Cloudflare via Main, and `GEOSITE,CN,DIRECT` selects the traffic exit. Exact domain and suffix DNS exceptions, proxy keyword policies and the international AI category precede CN. Split uses regional encrypted endpoints for explicitly listed domestic AI services. CN DNS coverage follows the client dataset, including any broad suffixes, upstream additions and misclassifications. Unknown domains follow the foreign default, and a general DIRECT traffic rule never automatically permits domestic DNS. The DIRECT outbound resolves destination names through the encrypted resolvers via Main unless an explicit DNS policy matches. The subsequent connection still uses DIRECT. Uncached lookups using Main require a working proxy, including when Unmatched selects DIRECT. Proxy-node bootstrap uses its own resolver configuration to avoid circular dependencies. The VPS also uses encrypted foreign DNS for destinations resolved server-side.

IPv4 DoH uses AliDNS (223.5.5.5 and 223.6.6.6), DNSPod (1.12.12.12) and Cloudflare (1.1.1.1). Bootstrap uses IP endpoints; node-specific policies reach all three operators directly. CN queries use Cloudflare via Main so an established proxy can reach it on networks blocking direct foreign DoH. These are concurrent upstream choices; operators may receive queries during normal operation. DNSPod recommends hostname access and may retire its legacy public IP; verify reachability from each client network. For IPv6 or DoT, bootstrap uses AliDNS and Cloudflare IPs; CN and node policies also use the DNSPod hostname, which requires working bootstrap on a cold start. Direct foreign DNS reachability still matters if all independent regional paths fail. Ordinary foreign and unknown queries have no domestic fallback. [DNSPod notice](https://docs.dnspod.cn/notices/mian-fei-ban-dot-dohbu-zai-gong-kai-ipjie-ru-de-gong-gao/)

The opt-in `singforge dns set --mihomo-policy domestic-first` uses encrypted IP endpoints to resolve DNS server names. Proxy-node DNS keeps its independent setting. Built-in domestic AI suffixes use regional encrypted resolvers via the AI-CN selection; selecting a proxy changes the connection to the resolver as well as the application exit. The resolver operators remain the configured regional providers for these explicitly permitted names. Smart routing uses the shared CN domain set for domestic DNS. Unmatched public names use encrypted DNS via Main or AI, including on a DIRECT business exit. A proxy outage causes uncached foreign lookups to fail closed. Smart routing additionally sends the GeoSite geolocation-!cn category to Main before the final GeoIP check; Unmatched applies only to remaining traffic. This policy affects full Mihomo profiles.

With preferred variants, Auto tests all nodes by latency and Main also exposes each node for manual selection. Without variants, Auto is an ordered fallback group. Main selects Auto first on a fresh import. Fallback priority is direct Reality Vision, direct Hysteria2, tunnel VLESS-WS, tunnel Trojan-WS, then remaining available nodes. Client-saved selections and Clash Verge merge profiles may override these settings. The connectivity-check URL measures node reachability; an AI service's regional or account availability is independent. Smart routing sends Apple TV to Streaming and common connectivity, push, time and update endpoints direct. Other Apple hosts follow normal precedence and the final policy.

Both Mihomo IPv6 switches default off for an ordinary IPv4 deployment. IPv6 resolver selection or an exclusively literal IPv6 node set selects IPv6 automatically unless overridden. Use `--mihomo-ipv6 on` to allow IPv6 with IPv4 resolvers on a tested dual-stack client. DNS family controls resolver reachability independently. Disabling AAAA in a proxy config cannot disable the OS IPv6 stack. TUN requires a capable client with service privileges; inspect the effective config after subscription refresh. Browser-specific DoH, excluded apps/interfaces, OS encrypted DNS and traffic before the client starts remain separate boundaries. Provider-only and URI exports cannot carry these DNS/TUN guarantees.

To reproduce DNS path checks, run `MIHOMO_BIN=/path/to/mihomo go test -count=1 -run TestMihomoLiveDNSPaths ./internal/render`. The test substitutes local TLS DoH recorders and a CONNECT proxy, queries fresh names, interrupts the proxy and checks which recorder received each question. Set `MIHOMO_TEST_TUN=1` only inside a disposable Linux network namespace with NET_ADMIN and /dev/net/tun. In that mode it sends UDP/TCP DNS packets to a test-network destination on port 53 to exercise actual TUN interception.

### Smart rule precedence and geographic data

User overrides are first. The smart preset then matches private addresses (including CGNAT 100.64.0.0/10), connectivity checks, basic ad blocking, international AI, domestic AI, streaming, communications and developer services. Ordinary domestic sites use the final CN geographic rules. Smart initially sends unmatched traffic through Main. The Gemini API and Apple captive portal use exact matches; service families such as YouTube CDN and Discord use suffix matches. AI-CN currently covers DeepSeek, Moonshot/Kimi, Qwen/Tongyi, ChatGLM/BigModel and Doubao domains. AI-CN is a separate selectable proxy group. Split mode sends its listed domains directly and resolves them with AliDNS/DNSPod over DoH/DoT. Strict mode resolves explicitly listed AI-CN domains via AI. The selected AI-CN group member controls the traffic exit.

`rules update` continues to refresh the smaller service lists used for AI, communication and streaming routing. It no longer downloads CN GeoSite or CIDR lists into SingForge state. Mihomo loads those datasets in its native format. Sing-box loads the upstream SRS files and caches them in its normal client cache. Geographic IP matches use `no-resolve`, so they don't trigger a DNS lookup to obtain an IP solely for country classification. Strict mode uses geographic data only for traffic routing.

### Node hostname bootstrap

If direct connections to the default encrypted DNS providers time out before a node can connect, use `singforge dns set --mihomo-node-dns alidns`. Full Mihomo exports then use a dedicated multi-operator encrypted DIRECT pool for the exact proxy hostnames. Each participating operator may see the client address and node hostname. Application DNS and traffic rules retain their own policies. An IP-only export needs no override. Use `--mihomo-node-dns default` to return to the normal international bootstrap resolvers.
